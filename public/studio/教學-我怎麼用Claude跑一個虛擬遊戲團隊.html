我如何用 Claude 跑一個虛擬遊戲開發團隊，
並且開發 Roguelike 射擊網頁遊戲

作者：Terry @ 南瓜虛擬科技 · 案例：Gorilla Gun Survivor · 2026-05-29

這份文件講「我如何把 AI 當虛擬團隊用，從零做出一款可玩的瀏覽器 3D 射擊遊戲」。 上面分頁切換主題：教學方法、遊戲本身、31 位虛擬團隊、原始啟動文件、進度管理、4 週 sprint、可下載範本。

痛點：AI 工具用了一段時間後...

  • 每次新對話都要重新解釋整個專案背景，超累
  • AI 跨對話會「失憶」— 上次拍板的決策下次可能違反
  • 一個 AI 同時當「策略 + 美術 + 程式 + QA」，沒人 review、容易失控
  • 進度不透明 — 不知道 AI 真的做了什麼、什麼時候該插手
  • 長時間離開後回來，AI 不知道之前做到哪
核心觀念：用檔案當所有 AI session 的共同記憶 + 把不同職責拆給不同「虛擬角色」 + 用 dashboard / mailbox / scheduled task 串成自動化團隊。

9 個關鍵手法

① 檔案即記憶

為什麼：AI 對話結束後記憶會消失。資訊只存在某次對話 → 下次找不到。
怎麼做：把所有決策、設定、進度、紀錄都寫成檔案。新 AI 開啟對話的第一件事就是讀檔。

② 規格驅動（OpenSpec 哲學）

為什麼：以前的設定散在 5 個地方，改一個要追到頭破血流。
怎麼做：一個東西一份檔。一把武器一份 .md、一隻怪物一份 .md、一張卡一份 .md、一位團隊成員一份 .md。

③ 角色分工（虛擬團隊）

為什麼：一個 AI 同時當「老闆 + 美術 + 程式 + QA」沒人 review、容易瞎搞。
怎麼做：每個角色寫一份 .md，內含：使命、職責、否決權、上司。AI 啟動時宣告自己是哪個角色。

④ 排程喚醒（Scheduled Task）

為什麼：Terry 不可能 24 小時在電腦前。AI 需要在他離場時自己推進。
怎麼做：用 Claude Cowork 的 scheduled task 每 30 分鐘喚醒新 Claude。新 Claude 讀循環指令檔，知道現在該做什麼。

⑤ 信箱通訊（mailbox）

怎麼做：建 inbox / outbox / broadcast 三個資料夾，正式管道發問與決策。

⑥ Dashboard 視覺化

怎麼做：寫一個 HTML 檔（用瀏覽器開），用白話 + 視覺方式呈現現況。看「📊 進度 Dashboard」分頁。

⑦ 停車規則（Stop Rules）

怎麼做：循環指令檔列出 stop conditions，每次喚醒先檢查。避免 AI 自動跑沒人看會出事。

⑧ 降載模式（Degraded Mode）

怎麼做：定義「卡住時可做的純文件工作清單」。AI 卡住時自動挑一項做，不會傻等。

⑨ 驗證分流（Sandbox vs Production）

怎麼做：明確區分「AI 沙盒能做什麼」vs「老闆 Windows 端必須驗什麼」。

完整流程示意

第 1 天：用 ChatGPT / Codex 起底

釐清專案輪廓、技術棧、團隊編制構想、產出啟動文件。

第 2 天：建檔案結構

建 openspec/、寫 project.md 紅線、AGENTS.md workflow。

第 3 天：寫所有實體 spec

武器、怪物、卡、元素、系統各寫一份 .md。

第 4 天：寫團隊角色

每位虛擬團隊成員寫一份 prompt 檔。

第 5 天：建 mailbox + dashboard

建信箱結構 + 寫 dashboard HTML。

第 6 天：設定 scheduled task

寫循環指令檔 + 在 Cowork 設 scheduled task 每 30 分喚醒。

第 7 天+：自動運作

老闆每天看 dashboard 5 分鐘、檢查 inbox、回 outbox 決策。其他時間 AI 自己跑。

常見陷阱與解法

陷阱 1：寫太多 AI 看的 spec，老闆看不懂

解法：規格給 AI、dashboard 給老闆。dashboard 一律白話、不引用 spec 術語。

陷阱 2：AI 開始亂發明角色

解法：角色清單寫死在 project.md，新增需老闆簽字。

陷阱 3：Scheduled task 跑太久、老闆失控

解法：每個任務內建「做完 N 個 slice 就停」+「STOP.txt 緊急停車」。

陷阱 4：AI 假裝 sandbox 驗證可信

解法：明文寫進 loop.md：「sandbox 驗證不算數，必須老闆在 Windows 上跑」。

陷阱 5：100+ 份檔，找不到

解法：建一份「總索引」(studio/索引.md) 列出所有資料夾用途。

陷阱 6：mount filesystem 對 git 不友善

解法：政策禁沙盒碰 git，只動檔案；老闆 Windows 端負責所有 git 操作。

適合 / 不適合用這套

✅ 適合

  • 長期專案（≥ 1 個月）— 投資建系統有回報
  • 多面向工作（程式 + 美術 + 行銷 + QA）— 角色分工才有意義
  • 老闆時間零碎（每天 30 分到 1 小時）— 自動化省時最有感
  • 需要可追溯（投資人 / 團隊要看進度）

❌ 不適合

  • 短期一次性任務— 直接用 ChatGPT 就好
  • 純創意發想— spec 框架會限制創意
  • 1-2 人小組緊密合作— 直接 face-to-face 比寫文件快

  • (1) 技術美術 TA 加入優化團隊 — 玩到後面會頓，這是 web 3D 的死穴
  • (2) 地圖設計師 加入 — 加入探索感、樓層、秘密路徑，但守住 roguelike 核心
  • (3) 行銷美術 加入 — 跟隨內容更新自動產出宣傳圖，質感由 CAO Raven 統一把關

核心紀律：這是 roguelike survivor，不是探險解謎、不是開放世界、不是 metroidvania。地圖再有趣，玩家的主軸永遠是「殺、撿、升、抽、撐」。任何改動偏離這條軸線，CEO 直接否決。

🗺️ 地圖設計鐵律（MAP DESIGN COMMANDMENTS）

#鐵律說明
0130 秒週長原則玩家全速跑一圈不超過 30 秒。地圖是戰場，不是迷宮。
02三層垂直性主層 (1F) + 高地 (2F) + 地下秘室。每層有戰術價值。
03秘密路徑 = 風險/報酬進秘密區要冒風險：破壞牆、開鎖、限時衝。
04秘密獎勵 ≤ 一次升級絕不能放神器或永久 buff，否則玩家會覺得「不探索就虧」。
05樓層切換不打斷節奏樓梯/升降梯/跳台必須 2 秒內完成。沒有過場、沒有 loading。
06地圖即視覺敘事叢林廢墟、實驗室、地下祭壇、霓虹都市 — 每張地圖都是世界的一面。
07三方協商機制Cartograph 任何設計提案必須通過 Systems + CAO + CTO 三方簽字。

📅 CEO 開的 4 週 Sprint 路線

本案 CEO Pumpkin King 在 launch brief 開的 4 週 sprint。這套節奏可參考套用到自己的專案。

W1 · 體檢與聖經建構
所有 agent 讀過 DESIGN.md，建立三本聖經
  • QA Analyst：跑遍既有原型、寫現況報告
  • CAO Raven：產出視覺聖經 v1
  • CTO Circuit：建立技術聖經 + 架構評估
  • Volt：建立 FPS / GC 監控儀表板
  • Cartograph：地圖設計提案 v1（3 種原型）
  • Scarlet：建立行銷素材模板與 prompt 庫

GATE: 三本聖經 + 效能基準

W2 · 地圖原型與優化基線
第一張新地圖原型 + 效能基線達標
  • Cartograph：「廢墟地圖」設計文件完成
  • 三方會議（CAO / CTO / Systems）簽字
  • Volt + Gameplay Programmer：子彈池、敵人池重構
  • Scarlet：第一份廢墟地圖宣傳圖產出

GATE: 廢墟地圖可玩 + 60fps 達標

W3 · 內容擴張
新增武器 / 怪物 / 第二地圖
  • Combat + Balance：3 把新武器設計 + 數值
  • Systems + Gameplay：5 種新怪物設計 + AI
  • Cartograph + Env Artist：洞窟地圖
  • SFX + Music：真實音效採購 / 製作開始
  • UI/UX：主選單、結算、暫停重做

GATE: 10 把武器 + 15 種怪物 + 2 地圖

W4 · 第一次重大評估
CEO 主持 milestone review
  • 是否仍守住 roguelike 核心？
  • 效能 / 美術一致性 / 數值平衡 / 內容多樣性全部審
  • 第一支 30 秒 trailer 草案
  • Steam 頁面草稿 v1
  • $15 定價可行性報告

GATE: 完整評估報告交給 Terry
